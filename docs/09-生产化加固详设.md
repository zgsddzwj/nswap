>    滥用（洗信用）由邀请码准入制兜底——重新加入需物业再发码。

## 2. P0 详设（上线阻塞）

### P0-1 图片对象存储化（最高优先：容器无状态，重启即丢图）

**现状**：`app/api/uploads.py::save_upload` 写容器本地盘；云托管容器重启/重新部署/扩容 → `uploads/` 目录清空，所有已发布图片、凭证图、头像变成裂图。代码注释已标注 TODO，本期落地。

**方案**：抽象存储层，双后端可切换。
```
app/services/storage.py
├── class StorageBackend(Protocol): save(data: bytes, ext: str) -> str   # 返回公网可访问 URL
├── LocalStorage(root, public_base_url)        # 现状逻辑（开发默认）
├── CosStorage(secret_id, secret_key, region, bucket, cdn_domain)  # 腾讯云 COS
└── get_storage() -> StorageBackend            # 按 settings.storage_backend 工厂
```
- **配置**（`core/config.py` + `.env.example`）：
  `STORAGE_BACKEND=local|cos`；`COS_SECRET_ID/COS_SECRET_KEY/COS_REGION/COS_BUCKET/COS_CDN_DOMAIN`
- **对象 key 规范**：`uploads/{YYYYMM}/{uuid}{ext}`（按月分目录，便于生命周期管理）
- **依赖**：`cos-python-sdk-v5`（纯 Python，`pip install --only-binary` 兼容）
- **两个上传入口统一改造**：multipart `POST /api/uploads` 与 base64 `POST /api/uploads/base64` 都调 `get_storage().save(...)`；返回 URL 语义不变（前端无感）
- **图片内容安全**：COS 自带公网域名，`mediaCheckAsync` 可直接访问（比本地盘更合规；本地后端保持现状）
- **存量迁移脚本** `scripts/migrate_uploads_to_cos.py`：扫本地 `uploads/` → 传 COS → 按前缀替换 `item_images.url`、`users.avatar_url`、`verify_requests.proof_image`（打印变更统计，支持 `--dry-run`）
- **验收**：单测用 FakeBackend 验证两入口调用与 URL 返回；COS 分支以"配置项就绪 + 未配置时行为不变"验收（无真实 COS 账号无法端到端，文档注明部署后自测步骤）；本地 local 后端回归 36 项不变。

### P0-2 管理后台登录防爆破 + 全局限流

**现状**：核实无任何限流；`POST /api/admin/auth/login` 可无限尝试；公共写接口（意向/留言/举报/上传）仅业务级频控（日发布数等），无通用速率限制。

**方案**：轻量限流中间件（内存实现，单实例准确；接口预留 Redis 后端供多实例）。
```
app/services/rate_limit.py
├── class RateLimiter(Protocol): hit(key, limit, window_seconds) -> bool
├── MemoryRateLimiter()      # 滑动窗口计数（默认）
└── 依赖注入：get_rate_limiter()
app/core/middleware.py
└── RateLimitMiddleware      # 全局兜底：每 IP 每分钟 120 次（超限 429）
```
**规则表**（写死为常量，便于调整）：

| 目标 | 键 | 限制 | 超限 |
|---|---|---|---|
| `POST /api/admin/auth/login` | IP | 5 分钟 10 次 | 429「尝试过于频繁，请 5 分钟后再试」 |
| 同账号连续失败 | username | 5 次 → 锁定 15 分钟 | 401「账号已临时锁定」 |
| 小程序写接口（wants/messages/reports/uploads/favorites） | openid | 每分钟 20 次 | 429 |
| 全局兜底 | IP | 每分钟 120 次 | 429 |

- 登录成功清空该账号失败计数；失败/锁定记 `admin_logs`（action=login_failed/login_locked）
- 测试环境：`settings.rate_limit_enabled`（默认 true；pytest 设 false，专门用例单独打开）
- **验收**：pytest 新增——6 次错误登录后第 6 次 429/锁定提示；正确密码在锁定期也被拒；正常登录不受影响；写接口 21 次/分钟被限；既有 36 项（限流关闭）全过。

### P0-3 数据库备份与恢复

**方案**（部署侧文档化 + 代码侧脚本，不改运行时）：

### P0-4 账号注销 + 协议同意记录（合规硬要求）

**数据模型**（迁移 `d9a4c1f83b72_production_hardening` 的一部分）：
- `users` + `agreed_terms_at` DateTime NULL、`agreed_terms_version` String(10) default ''、`deleted_at` DateTime NULL

**协议同意**：
- 常量 `TERMS_VERSION = "2026-10"`（`core/config.py`，与 agreement 页文案版本号一致）
- `POST /api/me/agree {version}` → 记录时间与版本；版本升级时（agreed_terms_version != 当前）小程序启动弹协议更新弹窗
- 小程序：`app.ts` 启动后若 `me.user.agreed_terms_version !== TERMS_VERSION` → 全屏协议弹窗（同意/退出），同意后调 agree 并继续
- **验收**：pytest——agree 落库；版本不符时 me 返回当前版本号供前端比对。

**账号注销**：
- `POST /api/me/delete`（需二次确认参数 `{confirm: "注销"}`）：
  1. 匿名化：`nickname="已注销用户{id}"`、`avatar_url=""`、联系方式三字段清空、`contact_enabled=False`
  2. 下架：在架/沉底物品 → archived；pending 意向 → rejected
  3. 保留（法务与对方权益）：交易与评价记录（展示为"已注销用户"）、信用统计（对方评价有效性）
  4. 状态：`status="deleted"`、`deleted_at=now`；openid 保留但登录时识别为已注销（`get_current_user` 对 deleted 用户返回 403「账号已注销」）
  5. 记 admin_logs（user_id + 时间，不含内容）
- 小程序：mine 页「账号与隐私」→「注销账号」→ 说明弹窗（列出将清除/保留的数据）→ 输入「注销」确认
- **验收**：pytest——注销后 me 403；联系方式已清；物品已归档；对方视角交易仍在且对方昵称显示"已注销用户"；重复注销 409。

### P0-5 可观测性（Sentry + 结构化日志 + 小程序错误上报）

**后端**：
- `sentry-sdk[fastapi]`；`settings.sentry_dsn`（默认空=不启用，本地零影响）；`ENVIRONMENT` 标签区分 dev/prod；`traces_sample_rate=0.1`
- 结构化日志：JSON formatter（`ts/level/logger/msg/request_id`）；`RequestIdMiddleware` 生成 `X-Request-Id` 注入日志上下文与响应头
- 慢请求告警日志：耗时 >1s 记 WARNING（path/method/status/耗时）
- 告警通道：Sentry issue 邮件/webhook（文档化配置步骤，写进 docs/05）
**小程序**：
- `app.ts` 注册 `wx.onError` + `wx.onUnhandledRejection` → `POST /api/telemetry/errors {message, stack(截断500), page, ua}`（限流 10/分钟/用户、只记日志不落库、不含用户内容）
- **验收**：未配 DSN 时 36 项回归不变且无 Sentry 网络请求；配 DSN 后人工抛异常可在 Sentry 后台看到（无账号 → 以"初始化代码 + 配置项 + 文档步骤"验收）；结构化日志本地可见 request_id 贯穿。

## 3. P1 详设（对外称生产级前应补）

### P1-6 审计日志查看页
- API：`GET /api/admin/logs?page&page_size&action?`——物业仅看**自己的**操作（admin_logs 无 community_id，按 admin_id 过滤）；超管看全部（含操作者名）
- admin-web：新增「操作日志」页（侧边栏，物业与超管均可见），列：时间/操作者/动作/对象/详情
- 验收：pytest（物业只见自己、超管见全部）+ 页面可查

### P1-7 内容安全人工处置闭环
- 现状：msgSecCheck 异常 → 文本 `sec_status=pending`（仅作者+管理员可见），但管理员**没有处置入口**，内容永久卡住
- 新增「待审内容」队列：
  - `GET /api/admin/pending-content?page`：本小区（超管全局）的物品与留言中 `sec_status=pending` 的条目（摘要/作者/时间/类型）
  - `POST /api/admin/pending-content/{kind}/{id}/approve` → `sec_status=pass`（正常展示）
  - `POST /api/admin/pending-content/{kind}/{id}/reject` → item: archived / message: hidden，并给作者发通知（type=`content_rejected`，前端加通知映射）
- admin-web：「内容审核」页（badge 显示待审数量）；sec-checks 页保持只读记录
- 验收：pytest（物业见本小区、放行后列表可见、拒绝后下架+通知、跨小区 403）

### P1-8 N+1 优化 + 复合索引
- **N+1**（核实：`item_card` 每行查一次社区名）：`serialize.py` 引入请求内社区名缓存——`item_cards`/各列表函数先批量查 `communities IN (...)` 构建 `{cid: name}` 传入；`user_summary(u, db, viewer, community_names=None)` 支持传入映射
- **复合索引**（迁移 `d9a4c1f83b72`）：`items(community_id, status, last_active_at)`、`items(user_id, status)`、`notifications(user_id, read, id)`、`dm_messages(conversation_id, id)`、`item_messages(item_id, status, id)`、`admin_logs(admin_id, id)`
- 验收：pytest 回归；新增查询计数断言（SQLAlchemy event 统计 `GET /api/items` 页的 SQL 数 ≤ 5，实施前基线 ~25）

### P1-9 CI/CD（GitHub Actions）
- `.github/workflows/ci.yml`，push/PR 触发三个 job：
  - `backend`：python 3.11 + pip install + `pytest tests/ -q`
  - `admin-web`：node 20 + `npm ci`（registry=npmmirror）+ `tsc --noEmit` + `vite build`
  - `miniprogram`：node 20 + `npm ci` + `tsc --noEmit` + 结构校验（把既有校验脚本固化为 `miniprogram/scripts/validate.mjs`）
- 验收：文件就绪 + 本地等价命令全绿（GitHub Actions 云端执行需推送后验证，文档注明）

### P1-10 运营工具
- **导出**：`GET /api/admin/invites/export`、`GET /api/admin/users/export` → CSV（UTF-8 BOM 防 Excel 乱码）；admin-web 加「导出 CSV」按钮
- **看板趋势**：`GET /api/admin/stats/trend?days=14` → 每日新增用户/物品/完成交易（`GROUP BY DATE(created_at)`）；admin-web 自绘轻量柱状图（div 高度，零新依赖）
- **公告增强**：`announcements` + `pinned`(bool default false) 字段；`PUT /api/admin/announcements/{id}` 编辑；列表排序 `pinned desc, id desc`；小程序公告卡优先取置顶
- 验收：pytest + 页面；导出文件本地打开无乱码

### P1-11 小程序端健壮性
- `app.ts`：全局错误上报（见 P0-5）
- `api.ts`：幂等 GET 失败自动重试 1 次（500ms 退避）；写请求不自动重试
- `chat.ts`：轮询连续失败 3 次 → 降频 5s→15s，成功即复位
- `upload.ts`：单张上传失败自动重试 1 次
- 验收：tsc + 结构校验；行为变更写入 miniprogram/AGENTS.md

### P1-12 容器与部署细节
- `Dockerfile`：创建非 root 用户 `appuser` 运行；`HEALTHCHECK` 指向 `/healthz`

## 6. 风险与开放问题

| 风险 | 处置 |
|---|---|
| COS/Sentry 无真实账号，端到端不可验证 | 以"未配置零影响 + 配置项就绪 + FakeBackend 单测"验收；部署后自测步骤写入 README |
| 内存限流多实例不准 | 单实例适用并注明；`RateLimiter` 接口预留 Redis 实现（P2） |
| 复合索引迁移锁表 | 数据量小无碍；迁移脚本注明大表用 `ALGORITHM=INPLACE` |
| 注销后交易展示 | 保留交易（对方权益），昵称统一"已注销用户"；如需完全清除另立合规流程 |
| 协议版本升级的用户体验 | 弹窗强制同意一次；版本号集中在 `TERMS_VERSION` 常量，前后端同源 |
| 开放问题：是否需要注销冷静期（7 天） | 本期立即生效；若合规或产品需要可后续加（保留 `deleted_at` 已为冷静期留位） |
